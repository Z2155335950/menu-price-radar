## 1. 使用规则

### 1.1 状态定义

| 状态 | 含义 |
|---|---|
| 未开始 | 还没有开始实现 |
| 进行中 | 正在实现，尚未通过验收 |
| 完成 | 已实现并通过本阶段验收 |
| 阻塞 | 有明确的外部问题导致无法继续，需要记录原因 |

### 1.2 推进规则

- 一次只推进一个阶段。
- 当前阶段完成后，更新本文档的状态和验收记录。
- 不自动进入下一阶段，等待用户确认。
- 如果阶段范围发生变化，先修改 `docs/AGENT_SPEC.md`，再修改本文档。
- 任何阶段都不能偷偷加入“明确不做”的功能。
- 每个阶段结束都要留下可验证的结果：页面、命令输出、测试或文档。

### 1.3 每阶段的回答结构

后续每个阶段都按照固定结构说明：

1. 本阶段目标；
2. 完成后会发生什么；
3. 为什么现在做；
4. 涉及的文件；
5. 实现内容；
6. 代码解释；
7. 操作和命令；
8. 验证；
9. 本阶段应该理解的内容；
10. 暂停并等待下一步。

  - 用户确认后，可以记住别名或换算关系；
  - 未解决阻塞项时不能继续改价。
- **为什么必须存在**：供应商名称不统一，单位包装又经常省略；错配会让成本计算整体失真。
- **主要文件**：
  - `src/domain/` 匹配规则；
  - 单位换算和包装换算；
  - 确认 API；
  - 确认界面；
  - 匹配和换算测试。
- **完成标准**：
  - 已确认别名可以自动匹配；
  - 一个名称对应多个食材时必须询问；
  - 包装缺少重量时必须询问；
  - 总价/单价矛盾时必须询问；
  - 异常价格必须确认；
  - 确认记录保存到数据库；
  - 确认前不能写价格历史；
  - AI 只给候选，不能代替用户确认。
- **范围控制**：不做密度自动推断，不做“一箱默认 10kg”。

### 阶段 8：确定性成本计算引擎

- **状态**：未开始
- **用户能看到什么**：
  - 测试命令输出一组成本用例；
  - 页面能看到某道菜涨价前后的单份食材成本、成本率和单份成本变化；
  - 缺销量时周影响明确显示为空。
- **为什么必须存在**：这是产品可信度的地基，必须独立于 AI、页面和数据库可测试。
- **主要文件**：
  - `src/domain/` 金额、单位、成本函数；
  - 表驱动单元测试；
  - 计算预览页面或接口。
- **完成标准**：
  - 金额使用整数微元，数量使用整数基础单位；
  - 公式与 `AGENT_SPEC.md` 一致；
  - 多食材汇总正确；
  - 缺售价、缺销量、缺历史价格、零销量等边界有测试；
  - 同样输入永远同样输出；
  - 不调用模型；
  - 不直接读写数据库，纯函数接收输入、返回结果。
- **关键测试**：
  - 包装总价换算；
  - 包装单价换算；
  - 斤和公斤换算；
  - 多食材汇总；
  - 缺销量返回 `null`；
  - 目标成本率缺失；
  - 四舍五入只发生在展示层。

### 阶段 9：风险检测与排序

- **状态**：未开始
- **用户能看到什么**：
  - 风险列表；
  - 严重、警告、观察、正常标记；
  - 有销量的菜按预计周食材毛利影响排序；
  - 缺销量的菜单独分组，并说明不能估算周毛利；
  - 每道菜能看到为什么排在这里。
- **为什么必须存在**：产品定位不是“算成本”，而是“告诉老板先处理哪道菜”。
- **主要文件**：
  - `src/domain/` 风险分级；
  - 分析服务；
  - 风险 API；
  - 最小看板页面；
  - 排序测试。
- **完成标准**：
  - 阈值集中配置；
  - 排序稳定，有明确次级排序；
  - 缺销量不生成金额；
  - 缺目标值有明确状态；
  - 数据质量警告和风险等级分开显示；
  - 同金额时排序结果可重复；
  - 所有分级和排序规则有测试。
- **待锁定参数**：
  - 严重：涨价后成本率比目标高 ≥ 5 个百分点，或周影响 ≥ 500 元；
  - 警告：涨价后成本率高于目标，或周影响 ≥ 200 元；
  - 异常价格：变化 ≥ 30%；
  - 置信度：关键字段 < 0.85 需要确认。
  - 这些默认值来自 `AGENT_SPEC.md`，阶段 9 用演示数据验证后可以调整，但必须同步文档和测试。

### 阶段 10：Agent 工作流和审计

  - 待确认项解决后才能继续；
  - 价格更新记录；
  - 计算快照；
  - 建议和证据的关联；
  - 失败后可以重试，不会重复改价。
- **为什么必须存在**：把提取、匹配、确认、计算和预警串成一条可解释、可恢复的流程。
- **主要文件**：
  - `src/agent/` 状态机；
  - 工具函数；
  - 审计记录；
  - 工作流 API；
  - 状态机测试。
- **完成标准**：
  - 状态转换符合 `AGENT_SPEC.md`；
  - 没有确认不能改价；
  - 改价和价格历史在同一事务；

  - 模型不能直接调用数据库写入；
  - 审计事件完整；
  - 不保存模型思维链。
- **范围控制**：使用自定义状态机，不引入 LangChain 或通用 Agent 框架。

## 6. 关键技术和产品决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 应用形态 | Next.js 全栈单项目 | 单人开发、单次演示、少一套前后端联调 |
| 语言 | TypeScript | 字段多、单位多，类型能减少错误 |
| 数据库 | SQLite + Node `node:sqlite` | 零数据库服务、单文件、易重置；当前 Node 24 已验证可用 |
| 数据访问 | 迁移 + SQL + 数据访问层 | 透明、可测试，不引入 ORM 隐式行为 |
| 包管理器 | npm | 系统已有 npm，避免额外配置 pnpm |
| 样式 | Tailwind CSS | 快速做出清晰的演示界面，不引入大型组件库 |
| 校验 | Zod | 统一 API 和模型输出的边界校验 |
| AI 接入 | 自定义适配层，默认 mock | 无 Key 可演示，真实模型可替换 |
| Agent 编排 | 自定义状态机 | 可审计、可测试、容易解释，不引入 LangChain |
| 金额 | 整数微元 | 避免浮点误差 |
| 数量 | 整数基础单位 | 单位换算可复现 |
| 风险阈值 | 集中配置 | 不把业务参数散落在 UI 和提示词里 |
| 测试 | Vitest | 启动快，适合纯函数和数据访问测试 |

## 7. 主要风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| Next.js 与 `node:sqlite` 构建不兼容 | 第二阶段曾列为风险 | 第二阶段已验证通过；后续升级 Node/Next 时重新跑健康检查和构建 |
| 图片/扫描 PDF 识别依赖多模态模型 | 第六阶段可能受限 | 先支持电子 PDF 文本；无视觉模型时用 mock 和样例，界面明确标注 |
| 模型提取不稳定 | 字段错误 | Zod 校验、置信度、证据、用户确认、失败兜底 |
| 单位/包装歧义 | 成本严重失真 | 不让系统猜；缺包装必须确认；不做隐式密度换算 |
| 缺销量被误算成损失 | 产品可信度受损 | 周影响返回 `null`，单独分组，页面明确说明 |
| 风险阈值过于武断 | 排序不符合预期 | 阈值集中配置，阶段 9 用演示数据校准并写回文档 |
| 数据模型过度设计 | 拖慢开发 | 只做当前链路需要的表；不做库存、采购、权限 |
| 页面最后才做导致整合困难 | 第十一阶段返工 | 从第五阶段起每阶段都有最小可操作页面 |
| 现场网络或模型不可用 | 演示失败 | 默认 mock；准备本地样例；准备粘贴文本兜底 |
| Windows 文件权限或环境异常 | 启动失败 | 第二阶段验证；保留环境检查命令和错误排查说明 |
