## 1. 产品定位

### 1.1 一句话定位

> **上传一张供应商报价单，自动找出哪些菜因为食材涨价正在亏钱，并按预计损失金额排序。**

### 1.2 产品要解决的问题

餐厅老板或采购人员通常能拿到供应商的新报价，但很难快速回答三个问题：

1. 这次涨价影响了哪些菜？
2. 哪道菜最值得先处理，损失大概是多少？
3. 这个结论是怎么从报价单一步步算出来的？

手工用 Excel 对比，容易漏掉菜、算错单位，也说不清依据。通用聊天机器人能读报价单，但它的计算不可重复，也不会主动停下来让用户确认模糊食材。

### 1.3 产品不是什么

这个 MVP 不是：

- POS 收银系统；
- 库存管理系统；
- 自动采购或自动下单工具；
- 自动修改菜单售价的工具；
- 完整财务记账系统；
- 菜品推荐或通用餐饮助手；
- 供应商自动聊天工具；
- 多门店、多角色权限系统。

它只把“**报价变价 → 找到受影响菜品 → 计算食材成本和风险 → 给出有证据的建议**”这一条链路做透。

### 1.4 MVP 成功的样子

演示者可以在 5 到 8 分钟内完成：

1. 打开网页；
2. 上传或粘贴一张虚构供应商报价单；
3. 系统提取食材、价格、包装、单位和证据；
4. 系统区分高置信度和低置信度字段；
5. 用户确认一个模糊食材或包装单位；
6. 系统写入新的食材价格；
7. 系统列出受影响菜品；
8. 系统显示涨价前后的单份食材成本、食材成本率和预计周食材毛利影响；
9. 系统按影响金额排序，突出风险最高的菜；
10. 点击菜品能看到报价证据和完整计算过程；
11. 系统给出和证据关联的下一步建议；
12. 所有关键计算通过自动化测试。

## 2. 目标用户和使用场景

### 2.1 目标用户

MVP 只服务一个角色：**餐厅的经营或采购负责人**。

这个角色：

- 看得懂菜名和报价，但不一定会写公式；
- 每周会收到供应商的新报价；
- 关心“哪道菜因为涨价不赚钱了”；
- 需要能向厨师长或合伙人解释结论依据；
- 不要求在系统里管理员工、门店或财务总账。

MVP 不实现登录和权限。演示时默认只有一个操作员，确认记录里使用一个可读的操作员名称，例如“演示操作员”。

### 2.2 典型使用场景

1. 供应商发来一张报价单图片、PDF，或者一段报价文本；
2. 用户在系统中上传或粘贴；
3. 系统提取报价行，并和餐厅标准食材匹配；
4. 遇到不确定的食材、包装或单位，系统暂停并提问；
5. 用户确认后，系统更新价格历史；
6. 系统找出用到这些食材的菜，计算涨价前后的成本；
7. 系统按预计影响排序，并给出有证据的处理建议；
8. 用户查看某道菜的报价证据、匹配依据和计算过程。

### 2.3 MVP 不解决的相邻问题

以下问题很重要，但不属于这一版：

- 今天应该进多少货；
- 哪家供应商整体更便宜；
- 菜品应该怎么定价才能覆盖房租和人工；
- 如何自动和供应商议价；
- 如何预测未来价格；
- 如何管理实际盘点损耗。

如果演示中被问到，应明确回答：当前版本只计算**核心食材成本**和**食材毛利影响**，不是完整经营利润。

## 3. MVP 范围

### 3.1 必须实现

| 编号 | 能力 | 说明 |
|---|---|---|
| M1 | 三种输入 | 报价单图片、PDF、直接粘贴文本 |
| M2 | 结构化提取 | 供应商、报价日期、原始食材名、数量、包装规格、总价或单价、单位、原始证据、置信度 |
| M3 | 标准食材匹配 | 把供应商名称匹配到餐厅标准食材 |
| M4 | 不确定项确认 | 食材、别名、单位、包装、价格口径不确定时暂停，等待用户确认 |
| M5 | 基础数据维护 | 标准食材、别名、单位换算、历史价格、菜谱用量、菜品售价、目标食材成本率、可选周销量 |
| M6 | 确定性计算 | 单份食材成本、食材成本率、单份成本变化、预计周食材毛利影响 |
| M7 | 风险排序 | 对所有受影响菜品按预计影响排序 |
| M8 | 有证据的建议 | 核对报价、议价、调整分量、调整售价、更换食材、继续观察 |
| M9 | 审计记录 | 报价原文、匹配依据、计算过程、用户确认记录 |
| M10 | 演示界面 | 能完成第 1.4 节整条流程的网页界面 |

### 3.2 明确不做

第一版不做：

- POS 自动接入；
- 完整库存管理；
- 自动采购和自动下单；
- 自动修改菜单售价；
- 完整财务记账；
- 菜品推荐；
- 供应商自动聊天；
- 通用餐饮助手；
- 复杂权限系统；
- 多门店管理；
- 多币种；
- 一个报价单里混合多个供应商；
- 净料率、损耗率、出成率；
- 税费分摊、运费分摊、折扣分摊；
- 菜谱版本树；
- 批量上传多份报价并自动合并；
- 邮件、短信、企业微信通知。

### 3.3 单次处理边界

一次处理只对应：

- 一家餐厅；
- 一个供应商；
- 一份报价；
- 一个报价日期；
- 一个操作员；
- 一个币种：人民币（CNY）。

报价可以有多行食材。多份报价需要分别处理，不做批量合并。

## 4. 默认假设

这些假设会影响数据模型、计算和演示。若后续修改，必须同步更新本文、`docs/DATA_MODEL.md` 和相关测试。

| 编号 | 假设 | 为什么这样定 | 如果假设错误，会影响什么 |
|---|---|---|---|
| A1 | 单餐厅、单币种、中文界面、本机演示、无登录 | 符合 MVP 规模和比赛演示条件 | 数据模型、接口鉴权、页面和部署方式 |
| A2 | 每种标准食材有一个基础单位，例如 g、ml、个 | 让价格和用量可以统一比较 | 单位换算、价格历史、成本引擎 |
| A3 | 报价单上的金额就是餐厅实际采购金额 | 不凭空推测税费和运费 | 报价模型、成本引擎、提取字段 |
| A4 | 税、运费、折扣只有报价单明确写出时才考虑，否则标记待确认 | 避免“算得很精确，但前提是编的” | 报价行字段、确认规则、成本口径 |
| A5 | 周销量可选 | 没有销量时不能编造周毛利损失 | 菜品模型、风险排序、页面展示 |
| A6 | 每道菜只有一个当前菜谱版本 | 第一版不做版本树 | 数据模型、成本引擎 |
| A7 | 报价日期是价格生效日期；缺失时必须确认 | 没有日期就无法判断“涨价前后” | 价格历史、风险计算 |
| A8 | 不做净料率、损耗率和出成率 | 这些会显著增加数据要求 | 菜谱用量、成本口径 |
| A9 | 运行环境为 Node.js 24 或更高 | 当前使用 Node 内置 SQLite | 数据访问层、启动环境 |
| A10 | 演示数据全部是虚构或匿名化数据 | 避免真实商业数据泄露 | 演示数据和演示脚本 |

### 4.1 关于“食材毛利”的口径

本产品计算的是：

> **菜品售价 − 单份核心食材成本 = 单份食材毛利**

它不是包含房租、人工、水电、平台抽佣和税费的完整经营利润。

页面和文档中优先使用：

- “核心食材成本”
- “食材成本率”
- “食材毛利影响”

避免使用：

- “净利润”
- “真实利润”
- “经营利润”

除非文案明确说明只是食材部分。

## 5. 输入与输出

### 5.1 输入

| 输入类型 | 限制 | 处理方式 |
|---|---|---|
| 粘贴文本 | 最多 20,000 字符 | 直接送入文本提取流程 |
| 图片 | JPEG、PNG、WebP，最大 10 MB | 保存原件；真实模式交多模态模型；mock 模式只支持内置样例图片 |
| PDF | 最大 10 MB，最多 5 页 | 提取电子文本并走文本提取；扫描件暂不自动 OCR，提示改用图片或粘贴文本 |

输入限制在第一版可以调整，但必须有明确提示，不能静默截断或丢弃。

### 5.2 输出

一次完整处理应产生以下结果：

1. **报价草稿**：供应商、日期、报价行、原文证据。
2. **字段置信度**：每个关键字段的高/中/低置信度。
3. **待确认项**：系统不能自动决定的问题，以及候选项。
4. **确认记录**：用户选了什么、什么时候、是否记住。
5. **价格更新记录**：旧价格、新价格、生效日期、来源报价。
6. **受影响菜品列表**：按预计影响排序。
7. **菜品计算详情**：涨价前后成本、成本率、单份变化、周影响、计算输入。
8. **行动建议**：每条建议引用报价证据和计算结果。
9. **审计时间线**：每一步做了什么、成功还是失败。

### 5.3 页面最终需要呈现的内容

- 报价输入区；
- 原文/原图预览；
- 提取结果表格；
- 置信度和待确认提示；
- 用户确认弹窗；
- 风险看板；
- 菜品详情；
- 计算过程；
- 报价证据；
- 行动建议；
- 处理记录。

## 6. 端到端流程

### 6.1 数据流

```text
报价文本 / 图片 / PDF
        │
        ▼
保存原件和原文
        │
        ▼
AI 提取：字段 + 证据 + 置信度
        │
        ▼
Zod 校验和业务校验
        │
        ▼
报价草稿（绝不直接改正式价格）
        │
        ▼
标准食材匹配 + 单位/包装换算
        │
        ├── 有不确定项 ──► 暂停，等待用户确认
        │                         │
        │                         ▼
        │                  保存确认记录
        │
        ▼
所有阻塞项已解决
        │
        ▼
事务写入新价格和价格历史
        │
        ▼
确定性成本引擎计算
        │
        ▼
风险分级 + 排序
        │
        ▼
有证据的行动建议
        │
        ▼
完整审计记录
```

### 6.2 Agent 状态机

状态代码用于后续实现和测试，页面可以用更自然的中文展示。

| 状态 | 含义 | 允许的下一步 |
|---|---|---|
| `created` | 已创建一次报价处理，尚未提取 | `extracting` |
| `extracting` | 正在提取字段 | `extracted` / `failed` |
| `extracted` | 字段已提取，等待校验和匹配 | `matching` / `failed` |
| `matching` | 正在做标准食材匹配和单位换算 | `awaiting_confirmation` / `ready_to_apply` / `failed` |
| `awaiting_confirmation` | 存在阻塞项，必须用户确认 | `ready_to_apply` / `failed` |
| `ready_to_apply` | 所有阻塞项已解决，尚未改价 | `price_applied` / `failed` |
| `price_applied` | 价格历史和审计已写入 | `analyzing` |
| `analyzing` | 正在计算成本和风险 | `analysis_ready` / `failed` |
| `analysis_ready` | 计算结果已保存 | `advice_ready` / `failed` |
| `advice_ready` | 建议已生成并关联证据 | `completed` |
| `completed` | 本次处理结束 | 无 |
| `failed` | 某一步失败，可重试或放弃 | 重试到失败步骤 / `completed` |

### 6.3 状态机硬规则

1. 只要还有阻塞性待确认项，不能进入 `ready_to_apply`。
2. 没有 `ready_to_apply`，不能写入价格历史。
3. 价格写入和价格历史必须在一个数据库事务中完成。
4. 价格写入成功后，重复点击“计算”不能再次写入价格。
5. 分析失败后可以重新分析，但不能重复改价。
6. 生成建议不能改变任何成本或价格数字。
7. 任何状态下都不能让模型直接执行数据库写入。

## 7. AI 与确定性代码的边界

| 任务 | 谁负责 | 说明 |
|---|---|---|
| 从文本/图片/PDF 中提取字段 | AI | 输出必须经过结构校验 |
| 判断字段是否可信 | AI 给置信度，代码套规则 | 置信度只是信号，不是事实 |
| 找到可能的食材候选 | AI 可以建议 | 规则和用户确认做最终决定 |
| 单位换算 | 代码 | 固定换算表和显式包装规格 |
| 包装规格换算 | 代码 | 不假设“一箱等于多少公斤” |
| 价格口径归一化 | 代码 | 总价/单价/每包装价必须明确 |
| 用户确认 | 用户 | 代码负责阻塞和记录 |
| 更新价格 | 代码 | 只允许在确认后通过服务层执行 |
| 单份成本、成本率、周影响 | 代码 | 纯函数，可自动测试 |
| 风险分级和排序 | 代码 | 阈值集中配置 |
| 行动建议的类型和事实 | 代码先算事实，AI 组织语言 | AI 不能编造数字 |
| 审计 | 代码 | 每一步持久化，不依赖模型记忆 |

### 7.1 AI 输出约束

- 只接受符合 schema 的 JSON。
- 可重试一次；仍然失败则展示错误和手动输入入口。
- 任何模型输出都视为“提案”，不是事实。
- 不保存模型内部思维链，只保存输入、结构化输出、提示词版本、模型名、耗时和错误。
- 不允许模型在建议中引入没有出现在证据或计算结果里的金额、百分比、单位。

### 7.2 为什么计算不能交给模型

即使模型“看起来算对了”，也存在：

- 同一输入多次结果不同；
- 无法稳定复现；
- 无法逐个用例测试；
- 出错时无法判断是提取错、换算错还是算术错；
- 不适合作为财务相关结论的唯一依据。

因此，模型可以解释结果，但不能生成最终成本数字。

## 8. 报价提取规范

### 8.1 每条报价行必须包含的字段

| 字段 | 含义 | 是否关键 | 例子 |
|---|---|---|---|
| `supplier_name` | 供应商名称 | 是 | 鲜源蔬菜配送 |
| `quote_date` | 报价日期 | 是 | 2026-11-01 |
| `currency` | 币种 | 是 | CNY |
| `item_name_raw` | 报价单上的原始食材名 | 是 | 去骨鸡腿 |
| `quantity_value` | 报价数量 | 是 | 2 |
| `quantity_unit` | 报价数量的单位 | 是 | 袋 |
| `package_spec_raw` | 原始包装描述 | 是 | 5kg/袋 |
| `package_quantity` | 每包装含多少基础单位 | 是 | 5000 |
| `package_unit` | 包装对应的基础单位 | 是 | g |
| `price_type` | 总价还是单价 | 是 | total |
| `price_value` | 报价金额 | 是 | 180.00 |
| `price_unit` | 金额对应单位 | 是 | 元/袋 |
| `line_total` | 行总金额（如果能确定） | 否 | 180.00 |
| `evidence` | 原文片段或文件页码/位置 | 是 | “去骨鸡腿 2袋 180元” |
| `confidence` | 字段和整行的置信度 | 是 | 0.92 |
| `notes` | 无法归类的原始描述 | 否 | “特价” |

### 8.2 “数量”和“包装规格”的区别

这是报价提取最容易出错的地方，必须区分：

- `quantity_value = 2`，`quantity_unit = 袋`：供应商报了 2 袋；
- `package_spec_raw = 5kg/袋`：每袋 5 公斤；
- 总基础数量 = 2 × 5kg = 10kg = 10,000g。

如果报价写的是：

- “10kg 180元”：数量是 10kg，包装规格可能没有写；
- “2袋 180元”：包装规格不明确，必须问“每袋多少公斤”；
- “2袋×5kg 180元”：信息完整，可以换算。

如果数量和包装互相矛盾，必须暂停确认。

### 8.3 价格口径

每条报价行最终都要归一化成：

> **每 1 个基础单位多少微元**

支持三种原始口径：

1. **行总价**：`price_type = total`，例如 2 袋共 180 元。
2. **基础单位单价**：`price_type = unit`，`price_unit = 元/kg`。
3. **包装单位单价**：`price_type = unit`，`price_unit = 元/袋`。

归一化规则：

```text
先算基础数量：
    如果 quantity_unit 是包装单位（袋/箱/包/件）：
        基础数量 = quantity_value × 每包装基础数量
    如果 quantity_unit 是基础单位或可换算单位（kg/g/斤/L/ml）：
        基础数量 = 把 quantity_value 换算成基础单位
    否则：
        暂停，要求确认

再算基础单位价格：
    如果 price_type = total：
        基础单位价格 = 行总价 ÷ 基础数量

    如果 price_type = unit 且 price_unit 是基础单位：
        基础单位价格 = 单价

    如果 price_type = unit 且 price_unit 是包装单位：
        基础单位价格 = 包装单价 ÷ 每包装基础数量
```

如果总价和单价同时出现且计算结果不一致，必须让用户确认以哪个为准。

### 8.4 证据要求

每条报价行至少保留一种证据：

- 原文中的文本片段和字符位置；
- 图片/PDF 的页码、区域坐标或截图；
- 用户手动修改前的原始提取值。

证据不能是模型“回忆”出来的。找不到证据的字段，置信度必须降低，并进入确认流程。

### 8.5 置信度

置信度范围是 0 到 1。

| 等级 | 范围 | 处理 |
|---|---|---|
| 高 | ≥ 0.85 | 没有其他歧义时可以自动继续 |
| 中 | 0.60 至 0.849 | 关键字段需要用户确认 |
| 低 | < 0.60 | 关键字段必须确认或重新输入；不能直接进入改价 |

关键字段：供应商、报价日期、原始食材名、数量、包装规格、价格、价格单位。

补充规则：

- 置信度是模型自报的，不能单独作为“正确”的证明。
- 即使置信度高，只要规则发现歧义，仍然要确认。
- 页面同时展示等级和数值，避免只给一个看似精确的数字。
- 用户修改后的值标记为“用户确认”，不再沿用模型置信度。

## 9. 标准食材匹配和单位换算

### 9.1 匹配优先级

从高到低：

1. 已确认的供应商别名精确匹配；
2. 标准食材名称精确匹配；
3. 标准化后的名称精确匹配（去空格、统一全半角）；
4. 已确认的模糊匹配；
5. AI 候选建议；
6. 没有匹配。

规则 1 到 3 可以由代码直接采用；规则 4 必须有历史确认记录；规则 5 只能作为候选项，不能自动改价。

### 9.2 必须暂停的匹配情况

- 一个名称匹配到多个标准食材；
- 完全没有候选；
- 候选置信度低于阈值；
- 别名和标准名称指向不同食材；
- 单位无法换算；
- 包装规格缺少关键数量；
- 价格口径不明确；
- 报价日期缺失或格式无法确定；
- 供应商缺失；
- 报价价格和历史价格差异过大；
- 报价日期早于当前最新价格，属于回填历史报价。

### 9.3 单位换算规则

基础单位只允许：

- 质量：`g`
- 体积：`ml`
- 计数：`个`（具体食材可以是“只”“枚”等，但必须映射到一个计数基础单位）

固定换算：

```text
1 kg = 1,000 g
1 斤 = 500 g
1 L = 1,000 ml
```

包装单位：

- `袋`、`箱`、`包`、`件` 不是固定重量；
- 必须提供“每包装多少基础单位”；
- 不允许系统默认“一箱 10kg”；
- 用户可以把“1 箱 = 10kg”保存为该食材的显式换算规则。

禁止隐式换算：

- 没有密度配置时，不能把 kg 和 L 互转；
- 没有食材专属换算时，不能把“个”直接变成 g；
- 如果确实需要“1 个 ≈ 250g”，必须由用户明确配置，并记录为换算依据。

### 9.4 异常价格检测

系统可以把本次基础单位价格与最近的历史价格比较：

- 有至少 3 条历史价格时，取最近 3 条的中位数；
- 不足 3 条时，取最近一条；
- 默认变化达到或超过 30% 时，标记“价格异常，请核对”；
- 阈值集中配置，不写死在页面里。

异常价格不是自动拒绝，而是阻塞项：用户必须确认“报价确实如此”或修正提取值。

### 9.5 历史价格和回填报价

- 新报价的生效日期默认取报价日期。
- 计算“涨价前”价格时，取生效日期之前最近的一条价格历史。
- 如果报价日期早于该食材当前最新价格，不能直接覆盖，必须提示这是历史报价并让用户确认。
- 没有历史价格时，可以保存新价格，但必须标记“缺少涨价前价格，无法计算变化”。
- 同一报价不能重复写入价格历史。

## 10. 用户确认规则

### 10.1 确认触发条件

| 类型 | 触发条件 | 是否阻塞改价 | 可记住 |
|---|---|---|---|
| `low_confidence` | 关键字段置信度 < 0.85 | 是 | 否 |
| `mapping_not_found` | 没有匹配到标准食材 | 是 | 是（别名） |
| `mapping_ambiguous` | 匹配到多个标准食材 | 是 | 是（别名） |
| `unit_unknown` | 单位无法换算 | 是 | 是（换算） |
| `package_unknown` | 包装规格缺少数量 | 是 | 是（换算） |
| `price_basis_ambiguous` | 总价/单价/单位不明确或互相矛盾 | 是 | 否 |
| `abnormal_price` | 价格变化超过配置阈值 | 是 | 否 |
| `missing_date` | 报价日期缺失或无法解析 | 是 | 否 |
| `missing_supplier` | 供应商缺失 | 是 | 否 |
| `backdated_quote` | 报价日期早于当前最新价格 | 是 | 否 |
| `new_ingredient_without_baseline` | 食材没有历史价格 | 否，但影响变化计算 | 否 |

### 10.2 确认记录必须保存

- 确认类型；
- 关联的报价和报价行；
- 系统问题；
- 提供给用户的选项；
- 用户最终选择；
- 用户修改前后的值；
- 是否记住；
- 操作员标识；
- 时间；
- 当时的证据。

### 10.3 “记住”的边界

可以记住：

- 供应商食材名 → 标准食材的别名映射；
- 包装单位 → 基础单位的换算关系。

不能记住：

- 某次报价的价格；
- 用户对异常价格的“这次没问题”判断；
- 对某个报价的临时修改。

“记住”必须由用户明确勾选，不能默认偷偷学习。

## 11. 计算规范

### 11.1 内部数值表示

为避免浮点误差：

- 所有金额在数据库和计算中使用**整数微元**：`1 元 = 1,000,000 微元`；
- 所有数量使用**整数基础单位**：g、ml、个；
- 单价使用“微元 / 基础单位”；
- 计算过程不做中间四舍五入；
- 最终展示金额时四舍五入到分（0.01 元）；
- 最终展示比率时保留 1 位小数百分比；
- 排序使用未展示的原始整数结果，不能用展示后的四舍五入值。

### 11.2 核心公式

```text
基础数量
    = 报价数量按包装或基础单位换算后的数量

基础单位价格（微元/基础单位）
    = 报价金额（微元）÷ 基础数量

单份食材成本（微元）
    = Σ（菜谱用量（基础单位）× 食材基础单位价格（微元/基础单位））

食材成本率
    = 单份食材成本 ÷ 菜品售价

食材毛利率
    = 1 − 食材成本率

单份成本变化（微元）
    = 涨价后单份食材成本 − 涨价前单份食材成本

预计周食材毛利影响（微元）
    = 单份成本变化 × 周销量
```

说明：

- 预计周食材毛利影响为正，表示**食材毛利减少**，即风险；
- 为负表示成本下降；
- 没有周销量时，该值必须是 `null`，不能是 0，也不能由模型补一个数字；
- 菜品售价在本次分析中保持不变，系统不会自动改菜单售价；
- 菜谱用量在本次分析中保持不变；
- 只考虑报价中实际发生变化、且菜品实际使用的食材。

### 11.3 涨价前后如何取数

- **涨价前价格**：报价生效日期之前最近一条价格历史。
- **涨价后价格**：本次报价归一化后的基础单位价格。
- **涨价前成本**：当前菜谱用量 × 涨价前价格。
- **涨价后成本**：当前菜谱用量 × 涨价后价格。
- 如果一道菜使用多个涨价食材，先分别计算每个食材的变化，再汇总为菜品总变化。
- 如果没有历史价格，不计算单份成本变化，页面显示“缺少涨价前价格”。
- 如果没有菜谱用量、售价或目标成本率，相关指标显示“无法计算”，不能补默认值。

### 11.4 缺失数据矩阵

| 缺少什么 | 仍可计算 | 不能计算 |
|---|---|---|
| 周销量 | 单份成本、成本率、单份成本变化 | 预计周食材毛利影响 |
| 目标食材成本率 | 单份成本、成本率、单份成本变化、周影响 | 是否超过目标的判断 |
| 菜品售价 | 单份成本、单份成本变化、周影响 | 食材成本率、基于成本率的分级 |
| 菜谱用量 | 无法计算该菜成本 | 所有该菜指标 |
| 历史价格 | 可保存新价格 | 成本变化和涨价影响 |

### 11.5 计算示例

假设：

- 去骨鸡腿：报价 2 袋 × 5kg，共 180 元；
- 基础单位是 g；
- 基础数量 = 2 × 5,000 = 10,000g；
- 新价格 = 180 元 ÷ 10,000g = 0.018 元/g = 18,000 微元/g；
- 历史价格 = 0.016 元/g = 16,000 微元/g；
- 每份宫保鸡丁用 180g 鸡腿；
- 售价 28 元。

则：

```text
涨价前单份鸡肉成本 = 180 × 16,000 = 2,880,000 微元 = 2.88 元
涨价后单份鸡肉成本 = 180 × 18,000 = 3,240,000 微元 = 3.24 元
单份成本变化 = 3,240,000 − 2,880,000 = 360,000 微元 = 0.36 元
涨价前食材成本率 = 2.88 ÷ 28 = 10.3%
涨价后食材成本率 = 3.24 ÷ 28 = 11.6%
```

这只是单个食材的示例，真实菜品还要把其他菜谱食材的成本相加。

## 12. 风险分级和排序

### 12.1 分析对象

风险列表只纳入：

- 在本次报价中价格发生变化；
- 菜品实际使用该食材；
- 菜谱用量存在；
- 单份成本变化为正（涨价导致成本增加）的菜品。

售价、周销量和目标成本率用于后续分级；缺少时可能进入“数据不足”，但不会因此伪造数据。

成本下降的菜品可以单独展示为“成本下降”，不进入风险损失排序。

### 12.2 风险等级

默认阈值集中配置，比赛演示使用以下默认值：

| 等级 | 代码 | 判定规则 |
|---|---|---|
| 严重 | `critical` | 单份成本增加，且满足任一：涨价后食材成本率 − 目标食材成本率 ≥ 5 个百分点；预计周食材毛利影响 ≥ 500 元 |
| 警告 | `warning` | 未达到严重，且满足任一：涨价后食材成本率 > 目标食材成本率；预计周食材毛利影响 ≥ 200 元 |
| 观察 | `watch` | 单份成本增加，但未达到严重或警告 |
| 正常 | `normal` | 没有涨价，或对菜品成本没有正向影响；用于对照展示，不进入风险损失排序 |
| 数据不足 | `insufficient_data` | 既无法用成本率目标判断，也没有周销量金额可判断，例如缺售价且缺周销量 |

补充规则：

- “数据不足”不是一个风险等级，而是数据状态，页面单独提示。
- 如果目标成本率缺失但有周销量，可以按周影响分级。
- 如果目标成本率存在但周销量缺失，可以按成本率分级，周影响显示为空。
- 如果售价缺失，成本率无法计算；但如果有销量，仍可按周影响分级。
- 如果目标成本率缺失且周销量缺失，即使有售价，也无法判断是否超过目标或金额影响，标记“数据不足”。
- 如果售价和周销量都缺失，无论目标成本率是否存在，都无法用成本率或周影响判断，标记“数据不足”。
- 数据质量警告（低置信度、异常价格）单独展示，不直接改变风险等级；它们影响用户是否应该先核对。

阈值必须放在配置中，不能散落在 UI 或提示词里。

### 12.3 排序规则

**A 组：有周销量**

1. 预计周食材毛利影响从高到低；
2. 食材成本率上升百分点从高到低；
3. 单份成本变化从高到低；
4. 菜品 ID 升序（保证稳定）。

**B 组：缺周销量**

1. 单份成本变化从高到低；
2. 涨价后食材成本率从高到低；
3. 菜品 ID 升序。

页面必须明确标注：

> “缺少周销量，无法估算周毛利，以下仅按单份成本变化排序。”

A 组整体排在 B 组之前，因为 A 组有更完整的金额影响信息。不能把 B 组的“单份成本变化”伪装成周损失金额。

### 12.4 展示要求

每个风险条目至少显示：

- 菜名；
- 风险等级；
- 预计周食材毛利影响（如果有销量）；
- 涨价前/后的单份食材成本；
- 涨价前/后的食材成本率；
- 目标食材成本率；
- 受影响最大的食材；
- 为什么被排在这里；
- 数据不足或数据质量提示。

## 13. 行动建议

### 13.1 建议类型

| 类型 | 适用情况 | 必须引用的事实 |
|---|---|---|
| 核对报价 | 低置信度、异常价格、价格口径不清 | 原始报价证据、异常幅度 |
| 议价 | 供应商涨价且该食材影响较大 | 旧价、新价、影响金额或成本率 |
| 调整分量 | 食材成本率明显超过目标 | 当前用量、成本率、目标值；不能编造建议克数 |
| 调整售价 | 有售价和目标成本率 | 当前售价、涨价后成本、目标成本率 |
| 更换食材 | 有可用替代食材数据时 | 替代关系和数据来源；没有数据时只能提示“可评估”，不能声称更便宜 |
| 继续观察 | 观察级风险，影响较小 | 当前变化和观察理由 |

### 13.2 建议的硬约束

- 每条建议必须关联至少一个证据或计算事实。
- 建议中的金额、百分比、单位必须来自确定性计算结果或报价证据。
- 不能建议“把售价改成某个数”却不给计算依据。
- 不能声称“更换食材一定更便宜”，除非系统里有该替代食材的价格数据。
- 不能把食材毛利说成净利润。
- 系统只给建议，不自动改价、不下单、不发消息。

### 13.3 可计算的建议事实

在数据允许时，可以计算：

```text
达到目标食材成本率所需的最低售价
    = 涨价后单份食材成本 ÷ 目标食材成本率
```

这个结果必须向上取整到分，确保达到目标，并明确标注“最低售价测算，不会自动修改菜单”。

如果目标成本率为 0 或缺失，不计算。

### 13.4 AI 失败时的兜底

如果模型无法生成建议：

- 仍然展示计算结果和证据；
- 用固定模板给出“核对报价 / 继续观察”等基础建议；
- 明确标记“建议文字生成失败，计算不受影响”。

## 14. 审计和数据处理

### 14.1 必须保留

- 上传的原始文件；
- 提取出的原文；
- 模型返回的结构化结果；
- 模型名称、提示词版本、耗时、错误；
- 每个字段的证据和置信度；
- 匹配候选和最终匹配依据；
- 用户确认记录；
- 价格变更前后的值和生效日期；
- 计算快照的输入和输出；
- 风险分级和排序依据；
- 建议文本和引用的证据。

### 14.2 不需要保留

- 模型内部思维链；
- 浏览器控制台日志；
- 与本次报价无关的聊天记录。

### 14.3 数据保留和重置

- MVP 数据保存在本机 SQLite 和本地文件目录。
- 提供“重置演示数据”的命令，但不提供复杂的删除和归档功能。
- 演示数据必须是虚构或匿名化的。
- 不在日志中打印完整 API Key。

| AC10 | 点击菜品 | 能看到报价证据、匹配依据和完整计算过程 | 10、11 |
| AC11 | 查看行动建议 | 建议与证据和计算结果关联，不出现无依据数字 | 10、11 |
| AC12 | 运行自动化测试 | 所有成本、单位、排序关键用例通过 | 8、12 |

## 16. 明确的产品判断

以下判断用于避免后续争论：

1. **宁可暂停，不要猜。** 不确定的食材、单位、包装、价格口径，必须问用户。
2. **宁可显示“无法计算”，不要补默认值。** 缺销量、缺售价、缺历史价格时，不编造。
3. **计算结果必须可复现。** 同一输入、同一版本，结果必须完全相同。
4. **建议必须能回到证据。** 没有证据的建议不展示为结论。
5. **模型是助手，不是账本。** 模型负责读和解释，代码负责算和写。
6. **演示优先。** 任何功能如果不能在 5 到 8 分钟内讲清楚，先不做。
7. **只做一条链路。** 报价变价导致哪些菜有食材毛利风险，先做透。
